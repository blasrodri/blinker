# Project Specification

## Incremental Mach-O Linker for Rust Development on Apple Silicon

## 1. Mission

Build a high-performance Mach-O linker in Rust, specialized for repeated Rust development builds on Apple Silicon.

The linker’s primary purpose is to reduce latency in edit–build–test loops performed by human developers, IDEs, and autonomous coding agents.

The project should optimize for:

```text
small source edit
→ partial Rust recompilation
→ incremental relink
→ runnable test binary
```

The principal success metric is not clean-link performance. It is the latency of repeated links after small code changes.

The desired product is:

> An agent-native incremental Rust linker for Apple Silicon that reuses persistent link state and turns repeated development links into fast, safe state updates.

---

# 2. Core Principles

Implement the project according to these priorities, in order:

1. Correctness
2. Safe fallback behavior
3. Measurable incremental-link improvement
4. Compatibility with common Rust development workloads
5. Maintainable architecture
6. Clean-link performance
7. Broad `ld64` compatibility

Never produce an executable when link correctness is uncertain.

When incremental reuse cannot be proven safe, perform a full internal link or delegate to Apple’s system linker.

Unsupported behavior must be explicit. Do not silently ignore unknown linker arguments, input formats, relocations, or Mach-O features.

# 3. Initial Platform Contract

The initial supported target is:

```text
Host:
  Apple Silicon Mac

Rust target triple:
  aarch64-apple-darwin

Output architecture:
  arm64 / ARM64

Output format:
  Mach-O 64-bit executable

Primary inputs:
  Mach-O object files generated by rustc/LLVM
  Rust .rlib archives
  Static .a archives
  Apple SDK .tbd stubs
  System dynamic libraries

Primary build modes:
  cargo build
  cargo test --no-run
  cargo test

Primary profile:
  Rust dev/debug profile

Link-time optimization:
  Disabled

Primary output:
  Command-line executable or Rust test executable
```

The official Rust target name is `aarch64-apple-darwin`, even though Apple commonly calls the underlying architecture `arm64`.

# 4. Product Scope

## 4.1 MVP goals

The first usable version must:

* Act as a Cargo-compatible linker executable.
* Accept the common linker invocation generated by `rustc` for `aarch64-apple-darwin`.
* Normalize and record linker arguments.
* Link ordinary non-LTO Rust debug executables.
* Read Mach-O ARM64 object files.
* Read Rust `.rlib` and static `.a` archives.
* Resolve symbols deterministically.
* Process the ARM64 relocations encountered in supported Rust builds.
* Resolve system-library imports through `.tbd` files or dynamic-library metadata.
* Generate a runnable Mach-O executable.
* Produce or arrange development-compatible code signing when required.
* Cache parsed metadata for unchanged inputs.
* detect changed inputs across repeated invocations.
* Reuse previous link state when safe.
* Fall back safely when incremental linking is invalid.
* Emit structured performance and fallback diagnostics.
* Pass differential runtime tests against Apple’s linker.

## 4.2 Post-MVP goals

Later versions may add:

* Fine-grained dirty-range output rewriting.
* Incremental symbol-resolution updates.
* Stable function and data addresses.
* Reserved output-layout slack.
* Branch islands or thunks when symbols move out of range.
* Persistent linker-daemon operation.
* Shared immutable caches across Git worktrees.
* Dynamic-library output.
* Dead stripping.
* Compact-unwind generation.
* dSYM and debug-map integration.
* Hot-reload experimentation.
* `x86_64-apple-darwin`.
* Universal binaries.
* ThinLTO integration.
* Additional Apple platforms.

# 5. Explicit Non-Goals for the MVP

Do not attempt to support the following in the first implementation:

* Complete compatibility with every `ld64` option.
* Intel macOS.
* iOS, iPadOS, watchOS, tvOS, or visionOS.
* Universal binaries.
* Swift applications.
* General Objective-C applications.
* Arbitrary C++ applications.
* Link-time optimization.
* ThinLTO.
* Dynamic-library production.
* Framework or application-bundle production.
* Kernel extensions.
* Bit-for-bit output equivalence with Apple’s linker.
* Historical Mach-O formats.
* Every ARM64 relocation ever defined.
* Runtime patching of an already-running process.
* Release-grade binary-size optimization.
* Production release signing or notarization.
* Replacing Apple’s linker for all workloads.

The project should be deliberately specialized.

# 6. Intended Users

## 6.1 Rust developers

Developers working on medium and large Rust projects should see lower latency after changing one or a few functions.

## 6.2 Coding agents

Coding agents frequently execute loops such as:

```text
inspect code
→ edit code
→ compile
→ link tests
→ run tests
→ inspect failure
→ edit again
```

An agent may perform dozens or hundreds of these cycles during one task. Saving even one second per cycle can materially reduce total task latency and compute cost.

## 6.3 IDE and editor tooling

The linker should eventually support persistent sessions initiated by editors or language tooling.

## 6.4 Hosted build infrastructure

A future daemon mode should permit a Mac build worker to reuse immutable dependency state across independent agent worktrees without sharing mutable outputs.

# 8. Development Strategy

Do not begin by attempting true byte-level incremental patching.

Implement the linker in progressively more capable stages.

## Stage A: transparent linker shim

Build an executable that:

* Accepts the linker arguments generated by `rustc`.
* Expands response files when encountered.
* Parses and normalizes known arguments.
* Records complete invocations for test fixtures.
* Delegates the actual link to Apple’s linker.
* Captures timing and input metadata.
* Produces reproducible linker-invocation corpora from real Rust projects.

This stage provides immediate information about actual Cargo and rustc behavior.

## Stage B: cold linker

Implement a complete internal link for a constrained Rust executable.

No persistent optimization is required yet.

The goal is semantic correctness.

## Stage C: cached full-output linker

Reuse parsed metadata for unchanged objects and libraries, but continue regenerating the entire output file.

This avoids repeated parsing without introducing complicated output patching.

## Stage D: incremental analysis

Incrementally update:

* Changed object metadata.
* Symbol providers.
* Archive extraction decisions.
* Dependency edges.
* Dirty sections.
* Relocation consumers.

The complete output may still be rewritten.

## Stage E: stable layout

Reuse the previous output layout when possible.

Reserve controlled amounts of growth space and avoid moving unchanged content.

## Stage F: dirty-range output updates

Write only affected output ranges when this can be done safely.

Global metadata may still be regenerated in full.

## Stage G: persistent daemon

Keep hot state in memory across invocations and support multiple worktrees safely.

Each stage must remain independently testable and benchmarkable.

# 9. High-Level Architecture

Use a Rust workspace with clearly separated components:

```text
rust-macho-linker/
  Cargo.toml

  crates/
    cli/
    driver/
    arguments/
    macho/
    archive/
    tbd/
    symbols/
    graph/
    layout/
    relocations/
    dyld/
    signing/
    cache/
    output/
    validation/
    daemon/
    diagnostics/
    benchmarks/
    test-support/
```

Suggested responsibilities follow.

## `cli`

* Program entry point.
* User-visible options.
* Exit-code handling.
* Diagnostic formatting.

## `driver`

* Coordinates one complete link.
* Selects cold, cached, incremental, or fallback mode.
* Manages transactional output replacement.

## `arguments`

* Parses rustc-generated linker arguments.
* Expands response files.
* Normalizes semantically equivalent arguments.
* Detects unsupported options.
* Generates the persistent-state key.
* Converts raw arguments into a typed link configuration.

## `macho`

* Safe parsing of Mach-O object files.
* Typed headers, load commands, sections, symbols, and relocations.
* Validation of all file bounds.
* Minimal architecture-specific abstractions.

## `archive`

* Reads `.a` and `.rlib` containers.
* Parses archive indexes.
* Performs lazy member extraction.
* Skips irrelevant Rust metadata members where safe.

## `tbd`

* Parses the subset of Apple `.tbd` text stubs required by supported builds.
* Extracts install names, exports, re-exports, architecture constraints, and platform constraints.

## `symbols`

* Maintains the global symbol table.
* Applies deterministic resolution rules.
* Reports duplicates and unresolved symbols.

## `graph`

* Maintains reverse dependencies among inputs, symbols, relocations, output regions, and metadata.
* Computes incremental invalidation.

## `layout`

* Assigns output sections and virtual addresses.
* Supports stable prior layouts and reserved slack.
* Detects when a full layout is required.

## `relocations`

* Decodes supported ARM64 relocations.
* Computes relocation values.
* Detects range overflows.
* Records reverse dependencies.

## `dyld`

* Generates the dynamic-loader metadata required by supported executables.
* Handles imported symbols and exported symbols.
* Encapsulates the selected dyld metadata encoding.

## `signing`

* Supports development-compatible output signing.
* May initially invoke an external signing command after internal linking.
* Must make signing behavior explicit and measurable.

## `cache`

* Persists parsed inputs and link state.
* Implements cache versioning.
* Performs safe deserialization.
* Handles corruption and invalidation.

## `output`

* Constructs Mach-O output.
* Tracks dirty byte ranges.
* Writes to temporary files.
* Performs atomic replacement.

## `validation`

* Performs structural output checks.
* Supports differential inspection against system tools.
* Provides optional post-link execution validation in tests.

## `daemon`

* Maintains in-memory state.
* Coordinates concurrent clients.
* Is not required for the first correct linker.

## `diagnostics`

* Human-readable diagnostics.
* JSON diagnostics.
* Timing spans and counters.
* Fallback explanations.

# 10. Linker Invocation and Argument Compatibility

The linker must begin by collecting real linker invocations from representative Rust projects.

Support should be driven by observed Rust workloads rather than by attempting to recreate all of `ld64`.

At minimum, investigate and support the argument categories generated for:

* Output path.
* Architecture.
* Deployment target.
* Entry point.
* Library search paths.
* Framework search paths when Rust dependencies require them.
* Static libraries.
* Dynamic libraries.
* `.rlib` files.
* System libraries.
* Undefined-symbol policy.
* Exported symbols.
* Dead-strip requests.
* Object-file lists.
* Response files.
* Platform and SDK configuration.
* Debug-build behavior.
* Linker-generated UUID behavior if present.
* Code-signing-related output behavior.

Normalize arguments before including them in cache keys.

Examples of equivalent inputs that should not create unrelated states include harmless differences in temporary paths when their content identity is unchanged. However, never normalize away arguments that could affect semantics.

Unknown arguments must result in one of:

```text
explicit unsupported-option error
or
documented delegation to fallback linker
```

Never silently discard them.

Persistent state must not be keyed only by workspace path.

The state key should include:

# 13. Input Fingerprinting

Use a two-stage fingerprint strategy.

## Fast path

Check:

```text
canonical or normalized path
file identity where available
file size
modification timestamp
```

## Verification path

Compute a content hash when:

* Metadata changed.
* The previous state is suspicious.
* Strict mode is enabled.
* Filesystem timestamp resolution is insufficient.
* The input comes from an environment where metadata cannot be trusted.
* Cache corruption is suspected.

Use a fast cryptographic content hash such as BLAKE3 for cache identity.

Suggested representation:

```rust
struct InputFingerprint {
    normalized_path: PathBuf,
    file_size: u64,
    modified_time_ns: u128,
    content_hash: Option<[u8; 32]>,
}
```

For archive members, include both archive identity and member identity.

Never reuse input metadata when freshness cannot be established.

# 14. Mach-O Object Parsing

Implement only the validated ARM64 object-file subset needed for supported Rust builds.

At minimum, parse:

* Mach-O magic and 64-bit header.
* CPU type and subtype.
* File type.
* Load commands.
* Segment and section records.
* Symbol table.
* String table.
* Defined symbols.
* Undefined symbols.
* Local symbols.
* Weak symbols and weak references.
* Section flags and alignments.
* Relocation records.
* Thread-local sections encountered in Rust builds.
* Unwind-related input sections when present.
* Build-version or platform metadata.
* Data-in-code metadata when required.
* Debug sections as opaque data or deliberately omitted data, depending on the selected debug strategy.

Every offset, count, multiplication, and range must be checked before access.

Malformed input must produce a structured error, not a panic or memory-safety issue.

Unsafe code should be:

* Minimized.
* Confined to narrow parsing or output primitives.
* Documented with explicit invariants.
* Covered by fuzz tests.

Prefer stable integer IDs and byte offsets over self-referential structures.

Example:

```rust
struct ParsedObject {
    id: ObjectId,
    fingerprint: InputFingerprint,
    architecture: Architecture,
    sections: Vec<InputSection>,
    symbols: Vec<InputSymbol>,
    relocations: Vec<InputRelocation>,
    metadata: ObjectMetadata,
}
```

# 15. Archive and Rust `.rlib` Handling

Treat `.rlib` files as first-class archive inputs.

Implement:

* Archive-header parsing.
* Long filename handling.
* Archive symbol-table parsing.
* Lazy member loading.
* Stable member identities.
* Cached archive indexes.
* Detection of Mach-O object members.
* Deliberate skipping of Rust metadata members that are not linker inputs.
* Deterministic extraction order.

Do not eagerly parse every member.

The symbol resolver should request an archive member only when the member may satisfy an unresolved symbol.

Incremental state must retain archive extraction decisions, but those decisions must be invalidated when:

* An unresolved-symbol set changes.
* A symbol provider disappears.
* A strong or weak definition changes.
* The archive itself changes.
* Library ordering changes.
* Relevant link arguments change.

Archive semantics are globally observable. Incorrectly retaining a previous extraction decision can produce a valid-looking but incorrect executable.

# 16. Symbol Resolution

Implement a deterministic global symbol table.

Support:

* Strong definitions.
* Weak definitions.
* Undefined symbols.
* Weak references.
* Local symbols.
* Global symbols.
* Private external symbols where required.
* Archive-provided definitions.
* Dynamic-library imports.
* Re-exported symbols when encountered in supported system libraries.
* Duplicate-definition diagnostics.
* Undefined-symbol diagnostics.

Use interned names and stable IDs:

```rust
struct SymbolId(u32);
struct SymbolNameId(u32);
struct ObjectId(u32);
struct SectionId(u32);
struct RelocationId(u32);
struct OutputRegionId(u32);
```

Example resolved representation:

```rust
struct ResolvedSymbol {
    id: SymbolId,
    name: SymbolNameId,
    provider: SymbolProvider,
    strength: SymbolStrength,
    visibility: SymbolVisibility,
    final_address: Option<u64>,
    dependent_relocations: Vec<RelocationId>,
}
```

Record enough provenance to explain why a symbol resolved to a particular provider.

Symbol-resolution diagnostics should identify:

* The symbol.
* Every competing definition.
* The selected definition, when one exists.
* The input files and archive members involved.
* The applicable resolution rule.

# 17. Incremental Dependency Graph

Maintain an explicit graph connecting:

```text
input file
→ input sections
→ definitions and references
→ archive extraction
→ resolved symbols
→ relocations
→ output sections
→ output byte ranges
→ dyld metadata
→ unwind metadata
→ code signature
```

The graph must answer:

* Which input files changed?
* Which sections were added, removed, or resized?
* Which symbol definitions changed?
* Which symbols changed providers?
* Which undefined symbols appeared or disappeared?
* Could archive extraction change?
* Which relocations depend on a changed or moved symbol?
* Which output regions are dirty?
* Which global metadata structures must be regenerated?
* Can the existing layout remain valid?
* Is incremental linking still safe?

Use a conservative invalidation policy.

False invalidation is acceptable because it only causes additional work.

Missing invalidation is unacceptable because it can produce incorrect executables.

# 19. Layout Strategy

## 19.1 Initial layout

The cold linker should produce a deterministic layout based on:

* Segment category.
* Section category.
* Alignment.
* Input order.
* Stable object identity.
* Stable section identity.

The output should be valid, not necessarily identical to Apple’s layout.

## 19.2 Stable incremental layout

After the cold linker works, retain prior placements where possible.

Each placed region should record:

```rust
struct RegionPlacement {
    region_id: OutputRegionId,
    file_offset: u64,
    virtual_address: u64,
    used_size: u64,
    reserved_size: u64,
    alignment: u64,
}
```

Reserve configurable growth slack around appropriate development-build regions.

When changed content still fits its reservation:

* Keep its address.
* Update its bytes.
* Reapply dependent relocations only where required.

When it no longer fits:

1. Attempt local expansion into adjacent free space.
2. Attempt placement in an extension area.
3. Optionally leave a branch thunk for moved code when safe.
4. Otherwise trigger a broader relayout.
5. Fall back to a full link when necessary.

Release builds should not use padded incremental layouts unless explicitly enabled.

# 20. Relocation Engine

Implement only the ARM64 relocation forms observed in the supported Rust workload corpus.

For each relocation kind:

* Parse it into a typed representation.
* Document its semantics.
* Validate its target and addend handling.
* Apply range checks.
* Record the symbol or section dependency.
* Provide an isolated unit-test fixture.
* Compare behavior with Apple-linked reference binaries where practical.

Example internal form:

```rust
struct InputRelocation {
    id: RelocationId,
    source_section: SectionId,
    source_offset: u64,
    target: RelocationTarget,
    kind: Arm64RelocationKind,
    addend: i64,
}
```

Unknown relocations must not be guessed.

They should cause:

```text
unsupported relocation
→ internal full-link path if supported there
or
→ system-linker fallback
```

When a target symbol moves, mark all dependent relocations dirty.

When branch displacement exceeds the supported range, either synthesize a valid thunk or abandon the incremental layout.

* `-L` search paths.
* `-l` library requests.
* Absolute dynamic-library paths.
* Apple SDK `.tbd` text stubs.
* Install names.
* Architecture filtering.
* Platform filtering.
* Symbol exports.
* Weak imports when required.
* Re-exports when required by supported inputs.

The output writer must generate a valid executable containing the required structures for the selected compatibility mode.

The exact set should be derived from experiments against supported Rust binaries, but will generally include:

* Mach-O executable header.
* Required segments.
* Required sections.
* Page-aligned file and virtual-memory layout.
* Entry-point metadata.
* Dynamic-loader path metadata.
* Required dynamic-library load commands.

# 23. Debug Information Strategy

Debug information can dramatically increase output size and complexity.

Choose and document one MVP strategy:

## Preferred initial strategy

* Preserve the input debug sections required for ordinary Rust debugging.
* Regenerate the complete debug-related output during cached full-output links.
* Do not attempt fine-grained incremental debug-info patching initially.
* Treat debug metadata as a broad invalidation region.
* Validate basic LLDB behavior against reference builds.

The MVP must state clearly which debugging features work.

At minimum, test:

* Breakpoint by function name.
* Basic stack traces.
* Source-line display where expected.
* Panic backtraces.
* Rust test-failure backtraces.

Full dSYM production may remain out of scope initially.

---

# 24. Unwind Information

Rust panic handling and stack unwinding may depend on unwind metadata.

The linker must not ignore unwind sections merely because the executable launches successfully.

The implementation should:

* Inventory unwind-related input sections from real Rust builds.
* Preserve or transform them according to the selected output strategy.
* Ensure addresses remain correct after layout.
* Invalidate relevant unwind records when code moves.
* Validate panic unwinding and stack traces.

If compact-unwind synthesis is not implemented initially, select a tested fallback representation that supports the targeted development workload.

---

# 25. Code Signing

Apple Silicon development executables may require valid signing-related output behavior.

The MVP should support one of these explicit strategies:

## Strategy A: external ad hoc signing

1. Internally generate the executable.
2. Atomically finalize the unsigned temporary output.
3. Invoke the system signing tool in ad hoc mode.
4. Validate success.
5. Replace the destination only after the complete pipeline succeeds.

## Strategy B: internal ad hoc signature generation

Implement only after the linker itself is correct.

External signing is acceptable for the MVP, but signing time must be measured separately because it can limit total incremental-link speed.

The linker must expose metrics such as:

```json
{
  "link_ms": 61,
  "sign_ms": 19,
  "total_ms": 80
}
```

Never modify the last known-good executable in place before a new signed output is ready.

Production identities, entitlements, notarization, and App Store workflows are out of scope.

# 26. Transactional Output

Every link must be crash-safe.

Use this sequence:

```text
load previous state
→ create temporary output
→ write or clone base output
→ apply link changes
→ finalize Mach-O metadata
→ sign when configured
→ validate structure
→ fsync when required
→ atomic rename to destination
→ commit persistent state
```

Do not patch the active executable directly.

A crash, cancellation, failed signature, failed validation, or full-link fallback must leave the previous valid output intact.

Persistent state should be committed only after the corresponding output succeeds.

Use generation identifiers to prevent mismatches between executable and state.

# 27. Persistent Cache Design

The cache should distinguish between:

## Immutable reusable data

* Parsed object metadata keyed by content.
* Parsed archive-member metadata.
* Parsed `.tbd` metadata.
* Interned symbol names.
* SDK metadata.

## Mutable link-target state

* Current symbol providers.
* Archive extraction decisions.
* Output layout.
* Dirty graph.
* Output-generation identity.
* Previous executable identity.
* Worktree-specific paths.

Cache requirements:

* Version every serialized structure.
* Include endianness and architecture assumptions where relevant.
* Validate lengths and checksums before loading.
* Treat corrupted cache entries as misses.
* Never panic because of corrupted cache content.
* Support complete cache deletion.
* Support bounded cache size.
* Expose cache-hit metrics.
* Avoid global locks during expensive parsing.

A cache hit must be an optimization only. Deleting the cache must never affect correctness.

---

# 28. Daemon and Agentic Workloads

The daemon is a later phase, but the architecture should not prevent it.

Suggested protocol:

```text
client sends:
  normalized link configuration
  ordered inputs and fingerprints
  output identity
  requested diagnostics mode

daemon returns:
  result mode
  output status
  timing metrics
  fallback reason
  state generation
```

The daemon must support:

* Multiple simultaneous worktrees.
* Multiple Cargo targets.
* Request cancellation.
* Per-session memory limits.
* Cache eviction.
* Concurrent read access to immutable parsed objects.
* Exclusive mutation of one logical link target.
* Crash recovery.
* Protocol versioning.

Do not allow two concurrent requests to mutate the same output state.

Use per-target serialization or optimistic generation checks.

---

# 29. Worktree and Multi-Agent Isolation

A typical agent infrastructure may create multiple Git worktrees for the same repository.

The system should use:

```text
shared immutable dependency cache
+
isolated mutable link state per worktree and target
```

State identity should include:

* Repository or workspace identity.
* Worktree identity.
* Cargo target identity.
* Output path.
* Profile.
* Target triple.
* Features and relevant flags.
* Link arguments.

A change in one worktree must never alter another worktree’s executable or mutable graph.

Shared cache entries must be content-addressed or otherwise proven immutable.

# 30. Fallback Design

Fallback is a core feature, not a temporary hack.

Support a configurable fallback linker:

```bash
rust-macho-linker \
  --fallback-linker /usr/bin/ld \
  ...
```

The exact system-linker path may differ by environment and should be discovered or configured rather than hard-coded blindly.

Fallback reasons should be structured:

```rust
enum FallbackReason {
    NoPreviousState,
    CacheSchemaMismatch,
```

# 32. Correctness Strategy

Correctness must be established through several independent methods.

## 32.1 Differential linking

For each fixture:

1. Link with Apple’s linker.
2. Link with this linker.
3. Compare meaningful binary properties.
4. Execute both outputs.
5. Compare observable behavior.

Outputs do not need to be byte-identical.

Compare:

* Architecture.
* File type.
* Load commands.
* Segment permissions.
* Section placement constraints.
* Imported libraries.
* Defined and undefined symbols.
* Entry point.
* Dynamic-loader metadata.
* Unwind behavior.
* Runtime exit code.
* stdout and stderr.
* Panic behavior.
* Test results.

## 32.2 Incremental versus cold equivalence

For every incremental scenario:

1. Create a clean build.
2. Apply a source edit.
3. Produce an incremental output.
4. Delete linker state.
5. Produce a cold internal output from the same final inputs.
6. Compare behavior and relevant binary semantics.

The incremental output must behave equivalently to the cold output.

## 32.3 System-linker fallback equivalence

For unsupported scenarios:

* Verify fallback receives the original semantics.
* Verify it produces the expected output.
* Verify exit codes and diagnostics are propagated.

## 32.4 Validation tools

Use available system inspection tools in tests to examine:

* Mach-O headers.
* Load commands.
* symbols.
* linked libraries.
* code signatures.
* architecture.
* runtime loading.

Tool output should assist testing, but correctness must not depend solely on fragile text parsing when a structured parser can be used.

# 43. Final Product Definition

The project should ultimately provide:
